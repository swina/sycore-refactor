- **Device PC: patch list follows recalled Solo Sets** — Recalling a named Solo Set (or clicking an assigned Solo Slot in Recall mode) previously only restored the slot data and sent the program change — the browser never moved, so the patch list kept showing whatever device/program was selected before. New `followSoloSlotInBrowser()` in `MidiDeviceProgramChangePanel.vue` genericizes the Performance-Set recall behavior for solo slots: it restores the slot's device registration state (`pcChannel`/`pcChannels`/`pcProgram`/`pcMsb`/`pcLsb`, reusing the registration's already-recorded bank name for that channel) so the bank/sound-list watchers rebuild the correct catalog bank and `scrollToCurrentProgram()` lands the highlight/scroll on the saved patch. Named-set recall targets the slot matching the currently selected device (fallback: first assigned slot); slot-pad clicks follow that slot directly. Branch `feat/08-30/Sycore-DSP-Integration-Feasibility`.
- **Live Input: new module, external audio input (Phase 6 of DSP integration, extension)** — A new **Live Input** module (Module Manager → Audio Tools, `Mic` icon, "Beta") lets a class-compliant USB audio interface, line-in, or mic feed sycore's own DSP: pick a device, hit Enable (one browser permission prompt), and the signal runs through the same Filter/FX-chain/Modulation-Matrix building blocks the drum machine and sampler already use. New `src/lib/live-input-engine.js` — a single continuously-open channel (`Tone.UserMedia → Filter → EffectChain → Panner → Gain(level) → Limiter → destination`), unlike drum/sampler's per-pad arrays. Everything in this chain is a Tone.js node (no native buffer-source stage), so none of the native/Tone `.connect()` boundary issues from the other engines apply here. `Tone.UserMedia` already disables echo-cancellation/noise-suppression internally (autoGainControl isn't controllable through that API — a known, accepted gap). Only the Modulation Matrix's **live** sources (lfo1/lfo2) apply — `velocity` has no note-on to resolve against on a continuously-open input, so it's filtered out before reaching `applyModMatrix()`. New `src/stores/useLiveInputStore.ts` (config + localStorage persistence) and `src/components/LiveInputPanel.vue` (device picker, level meter, Level/Pan/Filter knobs — no FX-chain or Modulation-Matrix cabling UI yet, same as Phases 2 and 5). Purely additive: no changes to any Phase 1-5 file. See `docs/plans/Sycore-DSP-Integration-Feasibility.md`.

## 2026-08-30

- **Drum Machine / Sampler: Modulation Matrix engine (Phase 5 of DSP integration, no UI yet)** — sycore's two existing LFOs (`useLfoStore.ts`, previously MIDI-CC-only) can now also drive local audio-rate modulation: `processLfo()` advances phase and pushes its raw waveform value (bipolar -1..1) into a new `lfo1Signal`/`lfo2Signal` regardless of whether that LFO is also targeting an external hardware parameter. New `src/core/audio/modMatrix.ts` + a small `ModMatrixSlot` catalog in `types.ts`, restricted to what actually applies to a drum/sampler pad — sources `velocity`/`lfo1`/`lfo2`, destinations `filterFreq`/`filterQ`/`ampVolume`/`ampPan`/`wetDryMix` — not Xynchrony's full per-voice catalog (patch glide, sample-start, key tracking, ...). Restructured from Xynchrony's single `applyModMatrix()` into two entry points because sycore's filter/padGain/panner/fxChain are shared/persistent per pad rather than built fresh per voice: `applyModMatrix()` rebuilds live `lfo1`/`lfo2` → `Tone.Scale` → param cables (editing-time, like `setPadFx()`); `applyVelocityModulation()` is a one-time nudge applied fresh on every trigger from each pad's cached true dial-in baseline (necessary since a live cable's `Tone.Scale` resets the underlying Signal's own intrinsic value on connect — reading `.value` back later would be wrong). Both engines gained `setPadModMatrix(padIdx, slots)`; drum tracks apply velocity inline in `triggerPad`/`triggerPadWithNote`/`triggerRatchet`, sampler pads read `pad._midiVelocity` (new, set by `SamplerPanel.vue`'s MIDI/app-note path alongside the existing `pad._midiNote`) fresh on every trigger. `DrumTrack`/`SamplerPad` gained `modMatrix?: ModMatrixSlot[]`. No cabling UI exists yet — same "engine plumbing, prerequisite for a future patch-cable editor" shape as Phase 2's FX chain. Known limitation, not fixed (unreachable without UI today): a destination with both a live LFO cable and a velocity slot can double-count its baseline. See `docs/plans/Sycore-DSP-Integration-Feasibility.md`.
- **Drum Machine: amp envelope; Sampler: envelope engine swap (Phase 4 of DSP integration)** — Drum tracks get a real Amp Envelope for the first time — **Attack/Decay/Sustain/Release** sliders in `DrumMachine.vue`'s FX strip, backed by a per-note `Tone.AmplitudeEnvelope` (drum hits are one-shot triggers, so unlike the pad-level filter/FX-chain, the envelope is created fresh per note and disposed when it ends, not shared across a pad). Sampler pads already had ADSR knobs and their own hand-rolled envelope (`_applyEnvelope`, manual `linearRampToValueAtTime` scheduling on a plain gain node) — `sampler-engine.js` now uses a real, persistent-per-pad `Tone.AmplitudeEnvelope` (`.triggerAttack()`/`.triggerRelease()`) instead, same architecture, no user-visible change. New `src/core/audio/envelope.ts`: unlike Xynchrony's own 6-stage, hardware-byte-encoded `Envelope`/`toAdsr()`, sycore's pads already store attack/decay/release in plain seconds and sustain normalized 0-1 (matching `SamplerPad`'s existing fields — `DrumTrack`'s new fields use the same convention, not Xynchrony's byte scale), so there was nothing to convert — the new file just guards against NaN/undefined reaching a `Tone.AmplitudeEnvelope`. Found and preserved (not fixed, out of scope) two pre-existing quirks while porting: sampler poly-mode notes on the same pad share one envelope instance, and `stopGranular()`'s release-fade doesn't actually reach granular voices' audio (they connect straight to the pad gain, bypassing the envelope). See `docs/plans/Sycore-DSP-Integration-Feasibility.md`.
- **Drum Machine / Sampler: filter resonance + type (Phase 3 of DSP integration)** — The per-pad filter is no longer a fixed lowpass-only, hardcoded-Q(0.5) `BiquadFilterNode`. Drum tracks and sampler pads each gained a **Resonance** dial (0-127, same byte convention as velocity/rootKey elsewhere) and a **Type** selector (lowpass/highpass/bandpass/low & high shelf/notch/all-pass/peaking) next to the existing cutoff knob — `DrumMachine.vue`'s FX strip and `SamplerPanel.vue`'s Filter panel. Ported Xynchrony's `resonanceToQ`/`resonanceToShelfGainDb`/`safeCutoffHz` math into new `src/core/audio/filterMath.ts`: resonance floors at Q≈0.707 (the standard "flat" response) rather than the old hardcoded 0.5, and shelf/peaking types additionally drive the filter's `gain` param (the only types WebAudio's `BiquadFilterNode` actually applies gain to) using the same Resonance dial as a 0-18dB boost. `setPadFilterType`/`setPadFilterResonance` added to both engines (`drum-engine.js`) or read fresh per-trigger from pad data (`sampler-engine.js`, matching how `filterFreq` already worked there) — no node reconstruction needed, both are live `Tone.Signal`/property updates on the existing per-pad `Tone.Filter` from Phase 1. Copy/paste FX (drum tracks) and FX-clipboard now carry the two new fields too. See `docs/plans/Sycore-DSP-Integration-Feasibility.md`.
- **Drum Machine / Sampler: per-pad FX chain engine (Phase 2 of DSP integration, no UI yet)** — Ported Xynchrony's `EffectChain`/`FxChain` node-graph (reverb, delay, chorus, 4-band EQ, compressor, phaser, each with its own dry/wet mix, wired Input → node(s) → Output with parallel branches allowed) into new `src/core/audio/effects.ts` + `types.ts`. Every drum track and sampler pad now has its own `EffectChain` instance spliced into the signal path between the per-pad filter and panner (`padGain → filter → fxChain → panner`), starting fully dry (`blankFxChain()`) so nothing sounds different yet. `DrumTrack`/`SamplerPad` gained an optional `fx?: FxChain` field, and both engines expose a new `setPadFx(padIdx, fxChain)` to rebuild a pad's chain. No FX editor UI exists yet — this is engine plumbing only, a prerequisite for a future patch-cable-style FX editor (same shape as Xynchrony's), see `docs/plans/Sycore-DSP-Integration-Feasibility.md`.
- **Drum Machine / Sampler: per-pad nodes migrated to Tone.js (Phase 1 of DSP integration)** — `drum-engine.js`/`sampler-engine.js`'s per-pad filter, gain, and panner (plus the sampler's envelope gain) are now `Tone.Filter`/`Tone.Gain`/`Tone.Panner` instead of raw `BiquadFilterNode`/`GainNode`/`StereoPannerNode`. Sample playback (`AudioBufferSourceNode`) and the per-note/per-grain transient gains stay native. Not user-facing on its own — it's the prerequisite so a future Modulation Matrix can connect `Tone.Signal` sources onto these params, first phase of porting Xynchrony's FX/Filter/Envelope/Modulation Matrix onto sycore's own drum/sampler audio (see `docs/plans/Sycore-DSP-Integration-Feasibility.md`). Also fixed the native→Tone connection points (a raw node's `.connect()` can't target a Tone.js wrapper directly — use its `.input`) and added proper `.dispose()` calls for the new Tone nodes in `sampler-engine.js`'s teardown.

## 2026-07-26

Incoming clock still drives the Incoming Clock BPM display, but can no longer fight the app's own generated clock on shared devices — fixes a MIDI-echo symptom (notes/CC repeating and fading out, often isolated to one channel) caused by a device broadcasting its own clock into the app.
- MIDI Flow: new **Settings** shortcut icon in the header opens the MIDI Manager window directly on its Settings tab.
- MIDI Controller Designer: **Virtual Instrument CC Table** — each virtual instrument can now have a named CC table (CC number + label, edited from a new button on its card in MIDI Devices). Named entries show up as an assignable action group in the Controller Designer's action picker, with a per-assignment Target Channel selector — useful since one CC table is shared across every channel of a multitimbral instrument, but a physical controller can usually only transmit on one fixed channel.
- Chord Prog Sequencer: **step copy/paste** — right-click any step in the grid for a small menu to copy its full parameter set (chord, notes, velocity, duration, gate, transpose, mode overrides) and paste it onto another step.

- MIDI Device Program Change panel: **Copy Map** — a new button next to a virtual instrument's name copies its entire 16-channel patch mapping onto another virtual instrument in one click, for setups where two virtual instrument entries route to the same standalone synth/app and should share identical per-channel patches.
- Performance: fixed audible Drum Machine / Chord Prog Sequencer stutter when a fader or knob is moved during playback — moving a control mapped to a mixer/virtual-instrument volume or a Sound Engine parameter was doing a synchronous `localStorage` write, a full controller LED resync, and a full re-render of every Sound Engine knob on every single incoming MIDI tick, which was enough main-thread work to stall Tone.js's Transport scheduling. All three are now debounced or deferred, so continuous CC input no longer disrupts playback timing.
